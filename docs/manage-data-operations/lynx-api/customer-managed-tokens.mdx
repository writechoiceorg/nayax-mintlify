Customer-managed access tokens let you grant limited, time-boxed API access
to your own downstream customers or integrations. Unlike the single
account-level token described in [Security & Token](/docs/manage-data-operations/lynx-api/security),
a customer-managed token carries specific permissions and an expiration date
that you define.

## Token Types

The system uses two related token types. A refresh token is long-lived and
is used only to request new access tokens. An access token is short-lived
and is the credential you actually send with each API call. Cortex Gateway
authorizes its own requests by converting the HTTP method and route into a
required scope string.

| Token type | Lifetime | Used for |
| --- | --- | --- |
| Refresh token | Up to 100 years | Requesting access tokens |
| Access token | 24 hours | Making Lynx API and Cortex Gateway requests |

## Scopes

A scope is a permission string that defines what a token can access. Scopes
follow the format `{domain}:{resource}:{action}`, where the domain and
resource identify what's being accessed and the action identifies the
allowed operation.

Common scope examples:

- `machines:read` grants read access to machine data.
- `orders:*:read` grants read access to all order-related resources.
- `users:app-token:create` grants permission to create app tokens.

<Warning>
Avoid granting the bare `*` scope. It grants full access to every resource
and action, which defeats the purpose of scoping a token to a specific
integration.
</Warning>

## Claim Types

A customer-managed token carries its permissions in one of three claim
types, each with its own priority and validation behavior.

| Claim | Purpose | Priority | Validation |
| --- | --- | --- | --- |
| `appScope` | Authenticates external services and integrations | Checked first | Must match exactly if present |
| `internalScope` | Authenticates internal Nayax microservices | Checked first | Must match exactly if present |
| `scope` | Standard OAuth2 user-level scope | Checked last, as a fallback | Checked after other authorization checks pass |

For most customer integrations, set `appScope` on the token to describe the
machines, devices, or orders the integration needs to access.

## Requesting a Customer-Managed Token

Nayax provisions customer-managed tokens on your behalf; you don't call an
API to generate one yourself.

<Steps>
  <Step title="Define the scopes">
    List the specific resources and actions the integration needs, using the
    `{domain}:{resource}:{action}` format described above.
  </Step>
  <Step title="Choose an expiration and name">
    Provide the expiration date and a descriptive name for the token, such
    as `Analytics Platform - Read Only`.
  </Step>
  <Step title="Receive your refresh token">
    Nayax issues a refresh token with the requested claims and expiration.
  </Step>
</Steps>

## Exchanging a Refresh Token for an Access Token

Once you have a refresh token, exchange it for an access token before making
requests. You can do this against either the Users API directly or the Lynx
API's pass-through endpoint, depending on which base URL your integration
already uses.

<Tabs>
  <Tab title="Users API">
    Send the refresh token as a standard `Bearer` credential.

    ```bash
    curl -X POST "https://users-api.nayax.com/v1/issue-access-token" \
      -H "Authorization: Bearer YOUR_REFRESH_TOKEN"
    ```
  </Tab>
  <Tab title="Lynx API">
    Lynx forwards this request to the Users API on your behalf. It expects
    the refresh token with a `jwt` scheme instead of `Bearer`.

    ```bash
    curl -X POST "https://lynx-api.nayax.com/v1/issue-access-token" \
      -H "Authorization: jwt YOUR_REFRESH_TOKEN"
    ```
  </Tab>
</Tabs>

<Warning>
The Lynx API endpoint expects `Authorization: jwt YOUR_REFRESH_TOKEN`, not
`Bearer`. Sending a refresh token with the `Bearer` scheme to this endpoint
fails.
</Warning>

Both endpoints return the access token in the same shape:

```json
{
  "Token": "eyJhbGciOiJSUzI1NiIsInR5cCI6IkpXVCJ9..."
}
```

Use this access token as a `Bearer` credential on subsequent Lynx API and
Cortex Gateway requests. For example, retrieving a list of machines:

```bash
curl -X GET "https://qa-lynx.nayax.com/operational/v1/machines" \
  -H "Authorization: Bearer YOUR_ACCESS_TOKEN" \
  -H "Content-Type: application/json"
```

## How Lynx Evaluates a Token

Cortex Gateway authorizes requests with a flat conversion from HTTP route to
required scope. For example, a `GET /v1/machines` request requires
`machines:read`, and a `POST /v1/machines` request requires
`machines:create`.

| Method | Route | Required scope |
| --- | --- | --- |
| GET | `/v1/machines` | `machines:read` |
| POST | `/v1/machines` | `machines:create` |
| PUT | `/v1/machines/{id}` | `machines:update` |
| DELETE | `/v1/machines/{id}` | `machines:delete` |

Lynx API applies a layered check instead of a single route-to-scope lookup.
For every request other than the token exchange described above, Lynx
evaluates the token in this order:

1. **`appScope` claim.** If present and it matches the scope required for
   the action, Lynx skips the remaining checks and allows the request. If
   present but it doesn't match, Lynx denies the request immediately.
2. **Menu-based permission check.** If no `appScope` claim is present, Lynx
   falls back to checking the calling user's menu permissions in Nayax Core.
   This is the same check used for standard account tokens.
3. **`scope` claim.** If the menu check passes, Lynx checks whether a
   `scope` claim is present and, if so, whether it matches. A mismatch
   denies the request even though the menu check succeeded.

The required scope string follows the same `{resource}:{action}` convention
as Cortex Gateway. For example, the `lynx_machines_get_machine` action maps
to `machines:read`.

## Security Best Practices

Follow these practices when requesting and managing customer-managed
tokens.

### Storage

Store refresh tokens in a secure key management system, or as environment
variables if you manage your own servers. Encrypt tokens at rest. Never
store a token in a plain text file, commit it to version control, or
include it in a URL.

### Scope and Expiration

Grant only the scopes an integration needs, and request the shortest
expiration that covers its use case.

### Token Limits

Nayax limits each user to 50 tokens.

## Troubleshooting

If a request using a customer-managed refresh or access token fails, check
the following common causes.

### 401 Unauthorized

The token is invalid or has expired. Verify the token hasn't passed its
expiration date and that you're sending it with the correct authorization
scheme for the endpoint you're calling.

### 403 Forbidden

The token's scopes don't include the resource or action you're requesting.
Compare the required scope for the endpoint against the `appScope`,
`internalScope`, or `scope` claims on your token, and request a token with
the missing scope if needed.

### 429 Too Many Requests

You've exceeded the rate limit. Cache and reuse access tokens for their
full 24-hour lifetime instead of requesting a new one on every call.
