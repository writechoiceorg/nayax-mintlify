Follow these steps to request a customer-managed refresh token and exchange
it for an access token you can use with the Lynx API and Cortex Gateway.

## Requesting a Token

Nayax provisions customer-managed tokens on your behalf; you don't call an
API to generate one yourself.

<Steps>
  <Step title="Define the scopes">
    List the specific resources and actions the integration needs, using the
    `{domain}:{resource}:{action}` format.
  </Step>
  <Step title="Choose an expiration and name">
    Provide the expiration date and a descriptive name for the token, such
    as `Analytics Platform - Read Only`.
  </Step>
  <Step title="Receive your refresh token">
    Nayax issues a refresh token with the requested claims and expiration.
  </Step>
</Steps>

## Exchanging a Refresh Token

Once you have a refresh token, exchange it for an access token before making
requests. You can do this against either the Users API directly or the Lynx
API's pass-through endpoint, depending on which base URL your integration
already uses.

<Tabs>
  <Tab title="Users API">
    Send the refresh token as a standard `Bearer` credential.

    ```bash
    curl -X POST "https://users-api.nayax.com/v1/issue-access-token" \
      -H "Authorization: Bearer YOUR_REFRESH_TOKEN"
    ```
  </Tab>
  <Tab title="Lynx API">
    Lynx forwards this request to the Users API on your behalf. It expects
    the refresh token with a `jwt` scheme instead of `Bearer`.

    ```bash
    curl -X POST "https://lynx-api.nayax.com/v1/issue-access-token" \
      -H "Authorization: jwt YOUR_REFRESH_TOKEN"
    ```
  </Tab>
</Tabs>

<Warning>
The Lynx API endpoint expects `Authorization: jwt YOUR_REFRESH_TOKEN`, not
`Bearer`. Sending a refresh token with the `Bearer` scheme to this endpoint
fails.
</Warning>

Both endpoints return the access token in the same shape:

```json
{
  "Token": "eyJhbGciOiJSUzI1NiIsInR5cCI6IkpXVCJ9..."
}
```

Use this access token as a `Bearer` credential on subsequent Lynx API and
Cortex Gateway requests. For example, retrieving a list of machines:

```bash
curl -X GET "https://qa-lynx.nayax.com/operational/v1/machines" \
  -H "Authorization: Bearer YOUR_ACCESS_TOKEN" \
  -H "Content-Type: application/json"
```

## Security Best Practices

Follow these practices when requesting and managing customer-managed
tokens.

### Storage

Store refresh tokens in a secure key management system, or as environment
variables if you manage your own servers. Encrypt tokens at rest. Never
store a token in a plain text file, commit it to version control, or
include it in a URL.

### Scope and Expiration

Grant only the scopes an integration needs, and request the shortest
expiration that covers its use case.

### Token Limits

Nayax limits each user to 50 tokens.

## Troubleshooting

If a request using a customer-managed refresh or access token fails, check
the following common causes.

### 401 Unauthorized

The token is invalid or has expired. Verify the token hasn't passed its
expiration date and that you're sending it with the correct authorization
scheme for the endpoint you're calling.

### 403 Forbidden

The token's scopes don't include the resource or action you're requesting.
Compare the required scope for the endpoint against the `appScope`,
`internalScope`, or `scope` claims on your token, and request a token with
the missing scope if needed.

### 429 Too Many Requests

You've exceeded the rate limit. Cache and reuse access tokens for their
full 24-hour lifetime instead of requesting a new one on every call.

For details on scopes, claim types, and how Lynx evaluates a token, see
[Customer-Managed Access Tokens](/docs/manage-data-operations/lynx-api/customer-managed-tokens).
