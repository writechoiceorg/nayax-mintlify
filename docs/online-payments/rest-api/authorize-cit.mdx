Most merchants process customer-initiated transactions (CITs) through the
Hosted Payment Page. Use this page instead only if you're building your own
checkout and submitting card or wallet data directly through the REST API.

## Prerequisites

This page uses the same endpoint as
[Authorize a merchant-initiated transaction](/docs/online-payments/rest-api/authorize-mit);
the only new requirement is PCI DSS certification, and only if you submit
raw card numbers.

<Warning>
  Submitting a raw card number (`paymentMethod.type: card`) through the API
  brings your systems into PCI DSS scope, typically SAQ D; see
  [PCI DSS scope](/docs/online-payments/prerequisites-and-onboarding#pci-dss-scope).
  Apple Pay, Google Pay, `scheme_token`, and `nayaxToken` carry no raw card
  number and don't trigger this. If you don't want that scope, use the
  Hosted Payment Page instead.
</Warning>

## Authorize a transaction

`POST /api/v1/transactions/authorize`

This is the same endpoint used for
[merchant-initiated transactions](/docs/online-payments/rest-api/authorize-mit),
with `transaction.initiationType` set to `cit` (the default, so you can omit
it) and `paymentMethod.type` set to `card`, `apple_pay`, or `google_pay`.
Every other field, `requestData`, `transaction.transactionType`,
`transaction.amount`, and so on, works the same as merchant-initiated
authorize.

| Method (`type`) | Parameter | Required | Format | Description |
| --- | --- | --- | --- | --- |
| `card` | `pan` | Yes | String, 12-19 characters | The card number. PCI DSS SAQ-D applies. |
| `card` | `expiryMonth` | Yes | String, 2 characters (MM) | |
| `card` | `expiryYear` | Yes | String, 2-4 characters (YY or YYYY) | |
| `card` | `cvv` | No | String, 3-4 characters | Card security code. |
| `card` | `cardholderName` | No | String, 1-200 characters | Name on the card. |
| `apple_pay` | `token` | Yes | Object | The Apple Pay `PKPaymentToken` from your own Apple Pay integration. Nayax decrypts it and processes it as DSRP. |
| `google_pay` | `token` | Yes | Object | The Google Pay ECv2 token from your own Google Pay integration. Nayax decrypts it and processes it as DSRP. |

Pass the `apple_pay.token` or `google_pay.token` object exactly as your own
Apple Pay or Google Pay integration returns it; don't reshape or unwrap it
first.

## 3D Secure

On the Hosted Payment Page, 3D Secure runs automatically and is the
recommended path for most merchants. If you authorize a card CIT through
the API with your own MPI/3DS already run, pass the authentication result
in `externalMPI` so Nayax forwards it to the acquirer and preserves the
liability shift.

| Object | Parameter | Required | Format | Description |
| --- | --- | --- | --- | --- |
| `externalMPI` | `eci` | Yes | String | Electronic Commerce Indicator (ECI) from your 3DS authentication. |
| `externalMPI` | `cavv` | No | String | Cardholder Authentication Verification Value (CAVV), the authentication cryptogram. |
| `externalMPI` | `dsTransId` | No | String | Directory-server transaction ID. |
| `externalMPI` | `messageVersion` | No | String | 3DS protocol/message version, for example `2.2.0`. |

## Response

The response uses the same fields as
[MIT authorize's response](/docs/online-payments/rest-api/authorize-mit#authorize-a-transaction):
`transactionId`, `status`, `authCode`, `declineCode`, `rawDeclineCode`,
`errorCode`, `amount`, `card.lastFour`, and `card.brand`.

```json
{
  "requestData": {
    "idempotencyKey": "idem_5c1e9a3f42",
    "orderId": "order_2051"
  },
  "transaction": {
    "transactionType": "sale",
    "amount": { "value": "4990", "currency": "USD", "exponent": 2 }
  },
  "paymentMethod": {
    "type": "card",
    "pan": "4242424242424242",
    "expiryMonth": "09",
    "expiryYear": "27",
    "cvv": "123",
    "cardholderName": "Jamie Rivera"
  }
}
```

```json
{
  "transactionId": "b3f8a1d2-6e4c-49a1-9c7d-1f2e8b6a3d5c",
  "status": "authorized",
  "authCode": "778899",
  "amount": { "value": "4990", "currency": "USD", "exponent": 2 },
  "card": { "lastFour": "4242", "brand": "VISA" }
}
```
